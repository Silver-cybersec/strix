## 2. 架构

结论：宿主进程驱动模型和工具；shell 在容器里跑；stdio MCP 在宿主跑。README 里的自动渗透和自动修复，靠的是容器内任意命令加上默认可写的源码挂载。

结论：本仓用 uv／Hatch 打 Python wheel，用 Dockerfile 打 Kali 沙箱，用 Go 编 TUI，用 npm 编 viewer。没有 compose，没有独立数据库，也没有写死的内存或 GPU 配额。未编译、未安装、未拉镜像。

- 构建：`Makefile` 29–33 行 `uv sync`；89–90 行 `uv build --wheel`；95–97 行 `CGO_ENABLED=0 go build` 出 TUI；84–86 行在 `strix/interface/viewer/frontend` 执行 `npm ci && npm run build`。打包钩子 `scripts/tui_sidecar_hook.py` 22–50 行同样调用 `go build`。沙箱镜像只有 `containers/Dockerfile`，没有 compose 文件。
- 语言与运行时：`pyproject.toml` 第 7 行 `requires-python >=3.12`。TUI `strix/interface/tui/go.mod` 第 3 行 `go 1.24.0`。前端 `package.json` 未钉 Node 版本；Dockerfile 64 行用发行版的 `nodejs`，版本不固定。镜像基础是 `kalilinux/kali-rolling:latest`（Dockerfile 第 6、33 行），其中的 Python 是发行版 `python3`，不是 3.12 的钉死版本。
- 数据存储：无独立数据库服务。代理会话写入运行目录里的 SQLite 文件 `agents.db`（`strix/core/runner.py` 302 行，`strix/core/sessions.py` 43–45 行）。
- 外部服务：扫描需要可用的 Docker 守护进程和 LLM API（`STRIX_LLM`／`LLM_API_KEY`，或 `strix auth` 的 ChatGPT 端点 `strix/config/codex.py` 42–50 行）。可选 Perplexity、Exa、Postman。云命令指向 `https://app.strix.ai`。镜像来自 `ghcr.io`。构建期还从 GitHub、npm、PyPI、`astral.sh`、`deb.debian.org` 下载，见 `audit/supply-chain.md`。
- 硬件：仓库没有 CLI 或沙箱的内存、CPU、GPU 最低要求。`docs/llm-providers/local.mdx` 15–18 行写本地模型「需要 GPU」，并说 70B 以下参数的模型难做代理；这是对操作者自备模型的说明，不是 Strix 进程的配额。沙箱内存／CPU／pids 只有设置了 `STRIX_SANDBOX_MEM_LIMIT` 等才生效（`strix/runtime/docker_client.py` 96–117 行），默认不封顶。
- 文档与代码不符：`docs/tools/sandbox.mdx` 87 行的 Playwright、33 行的 ZAP，镜像配方里没有。`docs/advanced/configuration.mdx` 80–81 行写 quick 模式把 `STRIX_REASONING_EFFORT` 降为 `medium`，代码默认始终是 `high`（`settings.py` 63 行），`runner.py` 457 行直接用该设置。同文档 76–77 行的 `STRIX_LLM_MAX_RETRIES` 在源码中没有这个名字；重试次数写死为 5（`strix/config/models.py` 687–688 行）。同文档 84、207–212 行的 `STRIX_MEMORY_COMPRESSOR_TIMEOUT`、`STRIX_SANDBOX_EXECUTION_TIMEOUT`、`STRIX_SANDBOX_CONNECT_TIMEOUT` 在 Python 源码中未找到读取点。`docs/usage/scan-modes.mdx` 的耗时没有对应实现。
